# Feature spec: Cycle counts

Status: **implemented and tested** (`CycleCount`/`CycleCountLine` in `domain`,
`CycleCountService` in `application` (reuses `StockMovementRecordingService` for posting
adjustments and `StockLevelRepository.lockOrCreateForUpdate` for the live-quantity read at
approval), mirrored JPA persistence in `infrastructure`, `CycleCountController` in `api`).
`V8__cycle_counts.sql`. 135 tests across the `api` module, all green, including
`CycleCountControllerIntegrationTest` (14 tests: FULL/SELECTION scope, the
open/count/approve-or-cancel lifecycle, both adjustment directions, no-adjustment on an
exact match, and role gating).

Scope: closes the second gap flagged when auditing domain completeness - a physical stock
count/reconciliation workflow. Builds on
[02-stock-movements](../02-stock-movements/requirements.md) (approval posts
`ADJUSTMENT_INCREASE`/`ADJUSTMENT_DECREASE` movements through that feature's own recording
service, never duplicating its validation or locking),
[06-roles-and-permissions](../06-roles-and-permissions/requirements.md), and
[07-audit-trail](../07-audit-trail/requirements.md).

## Decision

- **Scope of a session is implicit in the request, not a separate flag the client sets**:
  creating a cycle count with `productIds` omitted/`null` counts every product that currently
  has a `StockLevel` row at that warehouse (**full** count, including inactive products -
  a physical count covers what's actually on the shelf, not what's orderable); providing
  `productIds` counts only those (**selection**). The resulting session still records which
  kind it was (`scope`: `FULL`/`SELECTION`), for display, but the client never passes that
  enum directly.
- **Variance is computed against the system's quantity at *approval* time, not a snapshot
  taken when the session opened** (per the decision made when this feature was scoped): no
  snapshot is stored anywhere; `countedQuantity` is the only number this feature records
  per line, and the resulting adjustment reflects whatever `quantityOnHand` is the moment
  someone approves, not whatever it was when the count started. A real stock movement in
  between changes what adjustment gets posted - deliberate, not a bug.
- **One active state, `OPEN`** - unlike a purchase/sales order's multi-step chain, every
  mutating action on a cycle count (recording a line's count, approving, cancelling) has the
  exact same precondition ("the session is still `OPEN`"), so there is one state machine, not
  several action-specific ones: `OPEN` → `APPROVED` (posts adjustments) or `OPEN` →
  `CANCELLED` (posts nothing).
- **Approving posts one stock movement per line whose `countedQuantity` differs from the
  live system quantity** - `ADJUSTMENT_INCREASE` if counted is higher, `ADJUSTMENT_DECREASE`
  if lower, via `02-stock-movements`' own recording service (same transaction, same
  pessimistic lock, same existing rule that an `ADJUSTMENT_INCREASE` against an inactive
  product is rejected with `PRODUCT_INACTIVE` - inherited for free, not re-implemented here).
  A line whose count matches the system exactly posts nothing.
- This is **not** the same code path as the "bare" `ADJUSTMENT_INCREASE`/`ADJUSTMENT_DECREASE`
  via `POST /api/v1/stock-movements`, which
  [06-roles-and-permissions](../06-roles-and-permissions/requirements.md) restricts to `ADMIN`
  specifically because it has no order or count behind it. An adjustment generated by
  approving a cycle count *does* have something behind it - the count itself - so it is
  gated by `MANAGER` (who approves the count), not `ADMIN`. The two paths call the same
  recording service but are reached through entirely different application-layer code with
  independent role checks.

## Entities

- **CycleCount**: `id`, `warehouseId`, `scope` (`FULL`/`SELECTION`, set at creation per
  "Decision" above), `status` (`OPEN`/`APPROVED`/`CANCELLED`), `lines`.
- **CycleCountLine**: `id`, `productId`, `countedQuantity` (nullable - `null` until someone
  records a count for that line; re-recording while `OPEN` simply overwrites it).

## Endpoints

- `POST /api/v1/cycle-counts` - body `{ warehouseId, productIds? }`. Creates an `OPEN` session
  with one line per product per "Decision" above, every line's `countedQuantity` starting
  `null`.
- `GET /api/v1/cycle-counts` (paginated, filter by `warehouseId`, `status`),
  `GET /api/v1/cycle-counts/{cycleCountId}`.
- `POST /api/v1/cycle-counts/{cycleCountId}/lines/{lineId}/count` - body
  `{ countedQuantity }`. Records (or overwrites) that line's counted quantity.
- `POST /api/v1/cycle-counts/{cycleCountId}/approval` - requires every line to have a
  `countedQuantity`; posts the resulting adjustments; `OPEN` → `APPROVED`.
- `POST /api/v1/cycle-counts/{cycleCountId}/cancellation` - `OPEN` → `CANCELLED`, posts
  nothing.

## Roles (per [06-roles-and-permissions](../06-roles-and-permissions/requirements.md))

| Endpoint | Required role |
|---|---|
| `GET /api/v1/cycle-counts*` | STAFF |
| `POST /api/v1/cycle-counts` | STAFF (starting a count is executing a routine task) |
| `POST .../lines/{lineId}/count` | STAFF |
| `POST .../cancellation` | STAFF (discarding an unapproved count has no stock impact) |
| `POST .../approval` | MANAGER (the one action with a real consequence - see "Decision") |

## Audit (per [07-audit-trail](../07-audit-trail/requirements.md))

`CycleCount` is added to `AuditEntityType`. A `CREATED` entry on session creation; an
`UPDATED` entry on every recorded count, approval, and cancellation.

## Acceptance criteria

### Creating a session

1. `warehouseId` must reference an existing, active warehouse - `422` if unknown, `409`
   `WAREHOUSE_INACTIVE` if inactive.
2. `productIds` omitted/`null` → `scope = FULL`, one line per product with an existing
   `StockLevel` row at that warehouse (active or not), `countedQuantity = null` on every line.
3. `productIds` provided → `scope = SELECTION`, one line per given id. Each must reference an
   existing product - `422` otherwise.
4. The session is always created `OPEN`.

### Recording a count

1. Rejected with `409`, `CYCLE_COUNT_NOT_OPEN` unless the session is currently `OPEN`.
2. `lineId` must belong to the given `cycleCountId` - `404` otherwise.
3. `countedQuantity` must be `>= 0` - `400` (Bean Validation) otherwise.
4. Recording again for the same line while still `OPEN` overwrites the previous value - no
   history of earlier corrections is kept (the audit trail's `UPDATED` entries already show
   each successive value).

### Approval

1. Rejected with `409`, `CYCLE_COUNT_NOT_OPEN` unless the session is currently `OPEN`.
2. Rejected with `409`, `CYCLE_COUNT_INCOMPLETE` if any line still has `countedQuantity =
   null`. Nothing is posted.
3. For every line whose `countedQuantity` differs from the product's live `quantityOnHand`
   at that warehouse, posts exactly one `ADJUSTMENT_INCREASE` (counted higher) or
   `ADJUSTMENT_DECREASE` (counted lower) stock movement for the absolute difference, with
   `reference` set to the cycle count's id. A line whose count matches exactly posts nothing.
4. Inherits `02-stock-movements`' existing rule that an `ADJUSTMENT_INCREASE` against an
   inactive product fails with `409`, `PRODUCT_INACTIVE` - which, since this all happens in
   one transaction, rolls back every adjustment this approval attempt would otherwise have
   posted, including for lines processed before the failing one.
5. On success, status becomes `APPROVED`.

### Cancellation

1. Rejected with `409`, `CYCLE_COUNT_NOT_OPEN` unless the session is currently `OPEN`.
2. Posts no stock movements. Status becomes `CANCELLED`.

### Cross-cutting

1. List endpoints use the shared pagination envelope; every error the shared `ProblemDetail`
   shape.
2. Role requirements per the table above; every write produces the audit entries per
   [07-audit-trail](../07-audit-trail/requirements.md).

## Out of scope for this feature

- Any snapshot of the system quantity at the moment the session opens - see "Decision" above.
- Partial approval (approving only some lines) - approval is all-lines-or-nothing.
- Editing a line's `productId` or removing a line after session creation.
- Scheduling or recurring cycle counts - sessions are created on demand only.
